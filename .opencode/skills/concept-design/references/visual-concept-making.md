# Visual Concept Making: Build Concept

Use an iterative loop: understand the problem and scenario, make assumptions explicit, define criteria that can be checked later, build the concept model, inspect its consequences, and refine it with the student. A concept should say what capabilities and behavior are needed while preserving freedom in how they will be realized.

## Student-facing prompts

- Who is the user and in what situation does the product help?
- What value should the user experience?
- What must the product do for that value to be possible?
- Which feasibility assumption could make the concept fail?
- What observation or experiment would provide evidence for a criterion?
- Which elements describe logical responsibilities, and which already name a technology?
- What is a reusable definition, and what is one usage in this configuration?

## Model review

Trace important concept elements to assumptions or criteria. Check that relationships and behavior communicate the intended scenario, that each term has a clear meaning, and that a later PoC could be compared against the minimum specifications. Keep unresolved interpretations visible instead of quietly choosing for the student. Distinguish SysML language semantics from product-domain assumptions.

## Idea Wall example

The generic responsibilities are `Capture` (accept an idea), `Storage` (retain an idea), `Display` (show a selected set of ideas), and `Analytics` (identify useful relationships among ideas). The concept should not assume a specific phone, cloud service, database, display panel, or analytics vendor. Example assumptions include that participants can contribute from different locations and that related ideas can be identified. Turn each into a criterion that can be observed, then ask the student which responsibility or behavior addresses it.
